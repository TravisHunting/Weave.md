# Working on Weave

## Product and development

- Weave Server is an alternative host for the shared Rust library. Default Cargo feature `desktop` enables Tauri; headless builds use `--no-default-features --features server --bin weave-server` after `npm run build:server`. `server.rs` confines CLI workspace roots to direct children of `--workspaces`; desktop hosting freezes explicit selected workspace IDs and canonical roots (default selection is desktop-active workspaces), and browser restore opens the controller selection in each fresh tab. The server requires explicit scopes plus a server-instance header. Never expose desktop root grants, storage relocation, arbitrary export paths/templates, external-file writes or shutdown through HTTP. Git requests (`gitStatus`, `gitDiff`, `gitHistory`, `gitCommitDiff`, `gitIgnore`, `gitAction`) are allowed for scoped workspaces but always hardened: `server.rs` overwrites `args._host` with `{hardened:true, gitHosts}` (`--git-hosts`/`WEAVE_GIT_HOSTS`), and `backend.rs` `git_for` applies it to `native_git.rs`: hooks off (`core.hooksPath` = empty `<data>/git-keys/no-hooks`), only `https`/`http`/`ssh` protocols, no submodule recursion, `safe.directory` for the root, and Weave's `GIT_SSH_COMMAND` replacing any repository `core.sshCommand`. Never let a caller relax these or write inside `.git`. Authentication is per-workspace ed25519 deploy keys (`createDeployKey`/`removeDeployKey`, made by `ssh-keygen` in `<data>/git-keys/<workspace id>/`): status returns only the public key and fingerprint, and `known_hosts` there starts with GitHub's and GitLab.com's published host keys (`KNOWN_HOSTS`; others are accept-new). Setup actions are `configureIdentity`, `addRemote` (with `replace`), `testRemote` and `useRemoteBranch`; the guide is `app/weave/git-setup.mjs`. Desktop requests are not hardened but use a workspace's deploy key when one exists. Automatic snapshots (`snapshot`, `configureSnapshots`, `restoreFile`, `restoreSnapshot` Git actions; `gitHistory` takes `path`/`limit`/`skip` and marks Weave's commits by their `Weave-Snapshot` trailer; `gitCommitDiff` returns `files` and takes `path`) are scheduled by the backend `Monitor` from each workspace's `SnapshotClock`, never by the page; the standalone server sets `Backend::background_git` to its hardening so scheduled Git matches its requests. Background Git takes the workspace's `git` lock only with `try_lock`, never commits while anything is staged or during merges/rebases, stages explicit status paths (`.gitignore` applies, private data never), commits with `--no-verify` and no signing, and holds the `weave-snapshots.lease` in the repository's Git directory so one Weave process snapshots a repository. Hosts call `Backend::snapshot_on_exit` before setting `stopping`. Created workspaces (`create_workspace`, `serverOpen` with `create`) start with `Backend::start_history` (`git init`, snapshots on, push off). Run the Rust snapshot test and `npm run test:git` when changing them. Browser layouts, deactivation and sessions belong to each tab (`http-client.mjs`); a browser restores only workspaces it opened (desktop-managed servers: the controller's selection), never every registered one, and the start page lists the server's other folders (`serverFolders`, `#welcome-available`); server removal keeps files/settings. Preserve Origin/Host checks, JSON/custom-header requirements, bounds and CSP. Run `npm run test:server`, headless Rust tests and normal desktop checks for this boundary. `docs/SERVER.md`, Dockerfile and Compose files document deployment; remote Compose must remove every published origin port. Keep standalone server data separate from desktop data and workspace content. Desktop-hosted HTTP shares the desktop Backend, monitor, scopes and write locks; each workspace has independent desktop/server lifetime flags, and desktop layout persists only desktop-active roots. HTTP removal never closes a desktop workspace. `desktop` includes `server`; `--no-default-features --features server` must never pull Tauri, GTK, tray or WebView dependencies. Both binaries use `server::cli`; dispatch `weave server` before any desktop initialisation. `desktop_server.rs` owns controls/tray/background lifecycle; browser requests cannot call it. Its status lists the running server's accepted origins (`urls`), which Settings › Web server shows as links; the listen choice is a local/all toggle over `host` with an Advanced custom address. Tauri rejects with plain strings, so UI error handling must not assume `error.message`. Phones reach the server over plain-HTTP LAN addresses, which are not secure contexts: never call secure-context-only APIs (`crypto.randomUUID`, `navigator.clipboard`, …) unguarded; use `randomId()` from `platform.mjs`. `test:server` and `test:mobile` run without `crypto.randomUUID`. Rebuild both embedded pages with `build:desktop`. Run shared-host Rust tests and the native background/reopen tests when changing this boundary.

- Server authentication is shared in `server_auth.rs`, instance-level `auth/auth.sqlite`, independent of workspace caches. `auth.initialized` outside the auth directory distinguishes missing/damaged state from a new installation; never silently regenerate an existing identity. Use Argon2id, OS randomness, hashed session tokens, absolute/idle expiry, CSRF and persisted login throttles. Credentials and Turnstile changes revoke browser sessions. Local desktop/CLI administration uses the same store; never expose remote administration/reset. A new headless installation has no administrator: the first browser visit creates it (`setup` in `/api/auth`, open only while none exists, atomic via `Auth::initialize`), or `WEAVE_ADMIN_USERNAME` plus `WEAVE_ADMIN_PASSWORD`/`WEAVE_ADMIN_PASSWORD_FILE` create it at start and are ignored afterwards. Never generate or print passwords; `admin bootstrap` only reads files left by earlier versions. `WEAVE_ORIGIN` supplies `--origin` when that flag is absent (containers); the Dockerfile and Compose set no origin by default. A configured `--origin` is the only accepted origin and must be HTTPS unless loopback. The origin is optional for every listener. Without it, the headless server serves any plausible Host by default (`--allowed-hosts any`, `Config::any_host`), as self-hosted software usually does, and POSTs still need Origin equal to that Host plus the custom header, JSON type, CSRF and a session; an `https` Origin makes the session cookie `Secure`. `--allowed-hosts local` (`WEAVE_ALLOWED_HOSTS=local`), and always desktop hosting, accept only the derived origins (`Config::origins`): loopback plus this computer's own interface addresses (`interfaces.rs`, read at start) for `0.0.0.0`/`::`, or exactly the listen address. `Config::origins` also supplies the addresses shown in logs and Settings in both modes. Compose publishes `${WEAVE_PORT:-8765}` on all interfaces. Those plain-HTTP origins get non-Secure cookies, and Settings › Web server warns that network access is unencrypted. Turnstile validation fails closed, checks hostname/action and has bounded timeout/body/concurrency; public JSON never includes its secret. `/healthz` is minimal and public; content API/export and reader require authentication. There is no WebSocket route. Browser `W › Server account` opens password/logout controls without discarding reader drafts. Run authentication Rust tests, `test:server`, and native desktop background tests after changes. Docker builds must copy the fixed authentication assets as well as embedded reader pages, fetch crates only for the container's host target and keep the Tauri CLI out of the image's `npm ci`; Compose builds locally (`pull_policy: build`). The runtime image installs only `git`, `openssh-client` and `ca-certificates` (for Source control) and sets `HOME=/tmp` because the root filesystem is read-only; `test:server:container` checks Git, deploy-key persistence and that no build tools ship. `scripts/server/prepare-folders.sh`/`.ps1` create bind-mount folders (owned by UID 10001 on Linux) and write the ignored `compose.override.yaml`.
- Read `docs/USER_GUIDE.md` (behaviour, data folder, limits) and `docs/AUTHORING.md` (Markdown format) before changing indexing, storage or reader behavior. Use Node.js 24+ and npm scripts. Markdown is the source of truth; tree (`entries`), graph, search (`fts_<workspace>`), Kanban and count (`stats`) rows in `weave.sqlite` are disposable caches, but the same database holds durable sessions, workspace names/colours/order and Git preferences. Builds never edit articles.
- Keep Weave an article reader first, with useful prose, focused references and a small representative graph. Each source folder is a workspace. Several workspaces can be active at once (up to 12): each is watched and searched, has its own Files section, Git section, name and colour, and every desktop request carries its workspace's scope. Deactivated workspaces keep their cached rows and sessions and are reactivated from Control panel › Workspaces. Search interleaves all active workspaces by default; links, graph and Deep search stay within the workspace in use (the active tab's); a single tab can navigate between active workspaces, and Back/Forward skip entries of deactivated workspaces (they return on reactivation). Window-wide tab histories are saved in `workspaceLayout`, with `side: "right"` on the right split-view side's tabs plus `rightActiveTab` and `focus`.
- Keep multi-workspace behaviour covered by `npm run test:workspaces` and the Rust multi-workspace test when changing workspace, tab, session, split view or Git panel code.
- Split view shows two editor groups (`#editor-left`, `#editor-right`), each with its own tabs, editors, OKF bar and reading positions. The right group is cloned from the left at start-up with `-2` ids; list every per-pane id in `PANE_IDS` (`app/weave/panes.mjs`) and look per-pane elements up with `$p(id)` (the focused pane) or `pane.el[id]`, never `$(id)`. CSS is written for the left ids only: the build rewrites them to `:is(#id,#id-2)` (same specificity). The focused pane's state lives in the module variables (`tabs`, `active`, `live`, …) and `focusPane` swaps it; code that must reach every tab uses `allTabs()`/`paneTabs(pane)`. Only the focused pane holds unsaved text: leaving it hands the changes to the other side when that shows the same article, otherwise keeps a draft (saved at once unless autosave is off). An article open on both sides is mirrored with `LiveEditor.mirrorText`, and saves update both sides (`syncSaved`). The graph and Deep search belong to one pane (`graphPane`, `evidencePane`).
- Moves, renames, retitles, refreshes and changes on disk update open articles in place (`relocate`, `reloadChangedPanes`, `mirrorText`) rather than reopening them, which hides and lays out the article again and flickers.
- Responsiveness is an invariant, not an optimisation: no interactive request waits for indexing, scanning or Git, and interactive work is proportional to what changed or is shown, never to workspace size. Requests run concurrently on one `Backend` without a global lock. Per-workspace locks are `write` (file writes and index transactions), `scanning`, `git` and `plan`; hold `write` only for short critical sections (one index batch), never across a walk, a Git command or parsing. Reads go through `Database::read` (pooled WAL readers); index writes through `Database::write` (short transactions, `synchronous=NORMAL`, counts kept in `stats`), checking the planned hash before replacing rows. Reindex only affected paths (`reconcile_paths`, `index_written`); full scans merge the walk with `entries` in path order and read only changed files. Re-resolve links by filename key (`target_key`, `Database::resolver`); never build a whole-workspace resolver or read every article on an interactive path. Check new queries with `EXPLAIN QUERY PLAN` and pin indexes (`INDEXED BY`) where the planner would scan a workspace. In the reader, paths, titles, folders and link resolution come from the workspace's `CatalogIndex` (`ws.index`), kept current by `catalogChanges` deltas (`syncWorkspace`); never rebuild per-keystroke data from the whole catalog, and keep `tree.partial` (large trees load after the first article) working. After changing indexing, search, catalog, graph, startup or reader data flow, run `npm run bench:scale -- --docs 100000 --check` and, with Playwright, `npm run bench:ui -- --docs 100000 --check`; keep `scripts/performance-budgets.json` and `docs/PERFORMANCE.md` current.

Quick checks never replace the full checks listed below before delivery or distribution. Reserve release packaging for explicit distribution needs; `npm run package:all` (`scripts/Package-All.ps1`) builds the Windows package and then the Linux amd64 and arm64 packages in one run. `.github/workflows/release.yml` builds the Windows x64 desktop/server zips and the Linux amd64/arm64 `.deb`, `.tar.gz` and server `.tar.gz` on GitHub runners (arm64 natively on `ubuntu-22.04-arm`), reusing `Package-Windows.ps1 -SkipChecks` and `make-packages.sh` with the `toolchain.env` pins; a pushed `v<package.json version>` tag builds everything into a draft release, and a manual run builds only the outputs ticked in its form, tagging the built commit through the API and drafting a release when Create release is ticked (the `plan` job validates the choices and the tag first). Keep it in step when changing packaging scripts, package names or build dependencies. CI runs only unit and Rust tests, so it never replaces the full local checks. `scripts/README.md` › Requirements lists the build tools for each output; keep it current.
- After UI/build changes run `npm run build`, `npm test`, and available `test:browser`, `test:dynamic`, `test:desktop` and `test:workspaces` scripts (plus `test:git`, `test:graph`, `test:editor`, `test:tables`, `test:mermaid`, `test:layout` or `test:kanban` when those areas change). Inspect layout screenshots. Check the private runtime when host/services change. Builds and tests stay offline.
- Weave also ships for Linux (amd64 and arm64 `.deb`/`.tar.gz`, including Linux on ChromeOS), where the interface runs in WebKitGTK 4.1 instead of WebView2. `docs/LINUX.md` is the record of the build machine (WSL `Ubuntu-22.04`, set up by `scripts/linux/setup-build-env.sh`; pinned versions in `scripts/linux/toolchain.env`), reproducible packaging (`npm run package:linux`, `scripts/linux/package-linux.sh`) and Linux tests; keep it current when changing them. Keep platform code portable: gate Windows-only APIs with `cfg(windows)`, name the file manager neutrally off Windows ("Show in folder"), put a `system-ui` fallback after Windows fonts, and do not rely on WebView2-only behaviour. `verify-native.mjs` drives WebView2 over CDP on Windows and the app through `WebKitWebDriver` on Linux; run it there under `scripts/linux/with-display.sh` (private Xvfb, Openbox, forced X11). Browser suites launch through `app/weave/test-browser.mjs` with the repository's pinned Playwright devDependency (`WEAVE_PLAYWRIGHT` only overrides it; keep `PLAYWRIGHT_VERSION` in `scripts/linux/toolchain.env` equal to it, and keep it out of the Docker image) (`WEAVE_BROWSER`: Edge by default, `chromium`, or `webkit` to approximate WebKitGTK); keep CSP checks engine-neutral with its helpers. Tests must not rely on Chromium focus quirks: after clicking a button, focus the editor before keyboard editing (WebKit's Ctrl+A then selects the page, not the article), and keep geometry checks clear of wrap points that differ between engines' font metrics. Linux shell scripts and `packaging/linux/` files keep LF line endings (`.gitattributes`). The arm64 WebKitGTK headers conflict with the amd64 ones, so arm64 cross-builds run in `packaging/linux/arm64-cross.Containerfile`, never by adding arm64 to the build distro.
- The packaged desktop CSP carries hashes in `style-src`, so browsers ignore `'unsafe-inline'` and block inline `style="…"` attributes. Never put style attributes in generated HTML; set dynamic values through the CSSOM (`element.style.setProperty`) or data attributes painted by script. `test:workspaces` emulates this CSP.
- Interface skins (Settings › Appearance › Skin; appearance state `skin`, `data-skin` on the root) change shape, type, spacing and depth, never the palette: colour schemes own `--bg`, `--paper`, `--ink` and the other `colorFields`, written inline on the root. `app/weave/skin-contract.css` holds every token a skin may change, with Classic's values; Classic has no stylesheet and must stay pixel-identical to the contract. New appearance defaults and Restore defaults use Aurora Flow and Light grey; retain saved explicit choices. Write new chrome styling with contract tokens (`--radius-*`, `--shadow-*`, `--surface-*`, `--divider`, `--gutter`, `--control-border`, `--ui-font`, `--display-font`, `--ui-mono-font`, bar heights, `--icon-stroke`, `--ui-transition`, status colours such as `--danger` and `--warning`) rather than literals, adding a token when a skin needs a new decision. A skin is one entry in `app/weave/skins.mjs` plus `app/weave/skins/<id>.css`, appended by the build in registry order; every selector starts with `:root[data-skin~=<id>]` (or `.skin-preview[data-preview~=<id>]` for its picker miniature), and it sets only contract tokens or private tokens it uses itself (`tests/skins.test.mjs` enforces this). A skin may `extends` an earlier one: `data-skin` (and the miniature's `data-preview`) then lists the chain base first (`skinChain`), so the extending stylesheet states only differences. Scrollbars are part of the contract (`--scrollbar-*` for the article's own scrollbar, whose JS reads the track's CSS width; `--native-scrollbar-*` plus scoped `::-webkit-scrollbar` rules for the rest, since WebKitGTK ignores `scrollbar-color`). Tabs that merge into the editor use `--tab-curve` (concave feet drawn by `.file-tab.active::before/::after`) with an active tab the same colour as the surface below; keep the tab strip exactly `--tab-height` tall and hide the bands under it (`#graph-restore`, `#article-resize`) except on hover. The first frame must already show the saved skin, scheme and layout choices: `applyRootAppearance` (`appearance.mjs`) writes every root attribute and property, and `appearance-boot.mjs`, inlined by `build.mjs` as the first `<script>` in `<head>` (its hash in `script-src`), runs it from `localStorage` before the body is parsed; keep it small and free of CodeMirror and other heavy imports (hence `mermaid-palettes.mjs`), and put any new root appearance state in `applyRootAppearance` rather than only in the settings panel's `apply`. `test:browser` checks the root before the body. Prefer tokens over selector overrides so skins survive markup changes, and keep large translucent surfaces unblurred (blur only small overlays) for responsiveness. `test:browser` cycles every skin (`verifySkins`), checking the scheme is kept and the window is filled exactly.
- The start page (each pane's `#welcome`, shown in an empty tab) is how people find their next step on every host, phones included: `renderWelcome` in `ui.mjs` fills `.welcome-actions` with Create new workspace (`client.createWorkspace`: the desktop `create_workspace` command asks for a parent folder; the server uses `serverOpen` with `create`; hidden in exports, read-only hosts and desktop-managed servers), Open existing workspace (`#welcome-open` in the left pane; on a server that lists its folders, `#welcome-available` replaces it), and with a workspace New article, Random article (two or more articles), Set up Git (no repository) or Connect to GitHub (no remote) and, in the phone layout, Browse files. Offer only actions that are available now; never show disabled start-page buttons. Deactivated workspaces stay listed in `#welcome-recent` (on such servers the folder list covers them). Keep it cheap (it re-renders only when its HTML changes) and safe to call before a workspace's index or Git panel exists.
- The title bar keeps only the W menu (`#app-menu-button`, which opens `#app-menu`), Back and Forward at its start (`.titlebar-start`), and Graph (`#view-graph`, an on/off switch), the right-sidebar toggle, Edit and Source (`#source-toggle`, sharing `#source-mode`'s handler and pressed state; hidden in the phone layout, where the row has no room) at its end (`.titlebar-end`). Create workspace (`#create-workspace`), Open workspace, Set up Git (`#menu-git-setup`), Save, Reload, Source mode, Show article and Settings live in the W menu (older items keep their old ids), so tests click them with `menuItem(page, id)` from `test-browser.mjs`; the save status is in the status bar. Tabs in the title bar (appearance `titlebarTabs`, default on, root `data-titlebar-tabs`) is layout, not a skin, and works with every skin: `titlebar-tabs.css` (loaded after the skins) floats the title bar over the top row and starts the sidebars below it, and `titlebar-tabs.mjs` keeps each pane's strip clear of the control clusters (`--reserve-left/right`, measured in a ResizeObserver so tabs never show under the controls for a frame) and lets empty row space move and maximise the window. Tab bars stay inside their panes, so tab code is unchanged. With the graph showing, its lower edge (`#graph-resize`) is the only bar between graph and article; `#article-resize` appears only as the minimized article's strip, and dragging the bar below 60 px hides the graph entirely, leaving no bar, until Graph shows it again at its last height. `verifyTitlebarTabs` and `test:graph` cover this.
- The phone layout (root `data-layout="mobile"`, `MOBILE_QUERY` in `app/weave/mobile.mjs`: narrower than 760 px, or a short touch screen) is layout, not a skin, like Tabs in the title bar: `mobile.css` loads after `titlebar-tabs.css`, selects with `:root[data-layout=mobile][data-skin]` so it outranks skins, never sets colours, and changes no appearance preference (entering it closes both sidebars; the desktop window's 800 px minimum keeps the desktop app out of it). Starting with no article shown keeps the start page in view (its **Browse files** action opens the Files drawer), so its actions are visible at once; a drawer opened without a user gesture places the Back guard on the first touch instead. The rail and left sidebar form one drawer (`#mobile-drawer` in `.titlebar-start`, created only in this layout), the right sidebar another; one is open at a time, `#mobile-scrim` (inside `.shell`, below the title bar) closes them, and showing an article or Deep search closes them (`dismiss()`). Title-bar tabs are off in this layout (their CSS is gated with zero-specificity `:where(:not([data-layout=mobile]))`), split view shows only the focused side, Settings is a full-screen list/detail sheet (`data-view`), and Back pops a guard history entry: it closes the topmost dialog, menu or drawer, then goes Back in the tab, and leaves the page only when nothing is left; keep `history.replaceState` calls passing `history.state` and call `addressChanged()` after them. Touch drags in Files and tab strips scroll instead of moving (moves use Move…). Each side's tab bar slides away while its article scrolls down or is typed in and returns on scrolling up, at the top, on leaving the editor or when an article is shown: `data-tabs-hidden` on the editor group moves the whole group up by `--tab-height`, so skin-painted cards keep their shape; with the graph shown the sticky bar paints `--app-background` (fixed) under `--surface-tabbar`. The graph zooms with two-finger pinches (pointer events; `#graph` has `touch-action:none`), touchpad pinches (Ctrl+wheel, faster than plain wheel) and Safari gesture events. Keep controls at least 40 px in this layout and run `npm run test:mobile` when changing it, the sidebars, title bar, settings window or pane code.
- Export workspace fills `dist/export-template.html` (written by `npm run build:desktop`, embedded at compile time by `src-tauri/build.rs`) with one workspace's articles and graph, marked `portable`, and writes it only to a path chosen in the native save dialog; `exportWorkspace` is not in the page's request allowlist. Exports must stay read-only and request-free, and identical to Weave Lite apart from the embedded data. Rebuild the desktop shell before the executable so the template is current. Folder exports keep workspace-relative paths and turn links that leave the folder into unavailable targets. - Kanban lives in OKF frontmatter, never in SQLite alone: a board is any article with `type: Kanban Board` whose ordered columns (`id` stable, `title` displayed) are `weave.kanban.columns`; a card is any article with `weave.kanban.board` (the board's filename, unique per workspace, or a `./`/`../`/`/` path), `column` (a column id) and a sparse numeric `rank`. Never infer boards or membership from folders, never add a column or edit a board because of card data, and keep unplaceable cards visible (Needs attention lane, Kanban sidebar). `kanban.rs` and `database.rs` (`kanban_*` tables, schema 3) derive the index during reconcile; `app/weave/kanban.mjs` derives the same model for browser readers and does all frontmatter edits and rank planning (one card per move; renumber only that column when needed). Keep Rust and JS in step (`app/weave/tests/kanban.test.mjs` parity) and run `npm run test:kanban` (pointer-event drags, preview, menus, duplicates) when changing Kanban, frontmatter, rename or pane code. Writes go through `kanbanSave` after `ensureDraftsSaved`; board renames rewrite card `board` values in Rust's rename preview. Board names are unique among boards only: ordinary articles may share a board's filename. Articles dragged from Files onto a lane become cards there (`dropTarget`/`dropArticle` in `kanban-ui.mjs`, `externalAt` in the board view), gaining OKF frontmatter when they have none. Source mode always shows a board's Markdown (`boardShown` is false while `paneSource`). The board view (`kanban-view.mjs`, per-pane `kanban-view`) must not redraw mid-drag or when unchanged; the card preview is the right sidebar's `card` panel; settings live in Control panel › Kanban.
- Files Copy/Paste (menu or Ctrl+C/Ctrl+V while Files was used last) writes a copy through the native `copy` operation (in the page's request allowlist), which never replaces a path, refuses pasting a folder into itself, copies without the write lock and reindexes only the copy (`reconcile_paths`). Taken names gain “copy”; boards also do when another board has the filename. Between workspaces only articles are pasted (read, then `create`).
- Deleting is permanent unless Settings enables delete backups; never require saving before a delete. Users are expected to keep history in Git.
- Ctrl+F uses Weave's article find bar by default. The WebView find bar remains an option but only sees CodeMirror's rendered viewport, so it cannot search a whole article.
- `==highlights==` and `<u>underlines</u>` are parsed by the Lezer extensions in `app/weave/markdown-highlight.mjs`. Underlining is optional (Settings › Editing, preference `underline`, off by default): off, the `Underline` extension is not loaded (`LiveEditor` option `underline`, `refreshSyntax`), Ctrl+U does nothing, Format › Underline is hidden and `renderChatMarkdown(..., {underline:false})` keeps the tags literal. Both must keep behaving like bold (hidden marks, Home/Shift+Home, Ctrl+Backspace, formatting toggles; Ctrl+U underlines, and a whole `<u>`/`</u>` tag is one delimiter). Underlines stay the portable HTML tags; other inline HTML remains literal text. Their colour is one display preference (`highlightColor` in appearance), never written into articles. Paste (menu and Ctrl+V) converts formatted clipboard HTML to Markdown with `paste-markdown.mjs` (parsed inertly, never run); unformatted HTML, code positions and Paste as plain text (Ctrl+Shift+V) insert the plain text, and CodeMirror keeps handling plain pastes. The desktop window enables WebView2 clipboard access (`enable_clipboard_access`), so reading the clipboard never prompts. The editor context menu mirrors Obsidian's (Format, Paragraph and Insert submenus); keep its commands in `editor-formatting.mjs`, and do not offer Insert › Table when the right-clicked text is selected.
- Mermaid diagrams are a frontend feature (`app/weave/mermaid.mjs`, `mermaid.css`): the Rust backend treats ```` ```mermaid ```` fences as ordinary Markdown, and articles keep only the Mermaid source; never write generated SVG into a workspace. The pinned `mermaid` devDependency is minified separately by `build.mjs` and embedded in every page as inert text (`#weave-mermaid-runtime`, `type="text/plain"`, its hash in `script-src`; Tauri hashes every non-empty `<script>`), so start-up parses none of it; `mermaid.mjs` runs it as an inline script only when an article actually shows a diagram (`weaveMermaidStats.loaded`). Keep it out of the main bundle. Diagrams are CodeMirror block widgets drawn only when an `IntersectionObserver` sees them, one render at a time, cached (LRU) by `sourceHash(source)` and the theme key, and shown as an `<img>` of the SVG. Keep `securityLevel: 'strict'` in every configuration (`mermaidConfig`), and never insert Mermaid's SVG into the page DOM. The theme derives from the scheme colours, the skin's `--diagram-*` contract tokens and the Diagrams appearance preferences (`mermaid*`, written to root data attributes); appearance changes reach editors through `refreshMermaid` in `LiveEditor.requestMeasure`. Mermaid measures labels in the page, so `withInlineStyles` routes its style attributes through the CSSOM and its `<style>` through a constructed stylesheet while it renders under the hashed `style-src`; Chromium still reports refused styles for Mermaid's inert DOMPurify parse, against the document. ## Authoring knowledge

- When the user supplies project information without another explicit task, inspect related articles and update the appropriate knowledge. Use `.agents/skills/author-knowledge/SKILL.md`. Work in the library the user named; this repository supplies `knowledge-example/`, while standalone builds read `knowledge/` when present.
- Write self-contained Markdown about meaningful subjects. Start with a readable first-line heading and explain the subject's role. Preserve precise resource names in inline code when punctuation/underscores could be misread. Use readable filenames without appended IDs.
- An OKF frontmatter `title` supplies the file-tree, graph and link title; otherwise the first body-line heading (levels 1–6) does, then the filename. It is optional syntax but important UX: descriptive headings let readers navigate by title while filenames and incoming links remain stable. New articles start with a heading derived from the filename. Prefer changing a title over renaming a file when only its display name needs to change. The immediate parent folder supplies category and color; root articles use the workspace folder. Organize folders for clarity.
- Use OKF Markdown links with paths relative to the current article, starting with `./` or `../`, forward slashes and `.md`: from `infrastructure/compute/vm-shir-01.md`, write `[sqldb-warehouse-prd](../data-stores/sqldb-warehouse-prd.md)`. Weave also reads OKF bundle-relative `/infrastructure/databases/ods_prod.md`, but write relative paths for compatibility with ordinary Markdown readers. Do not use filesystem paths, entity IDs, `[[...]]` wiki links or `@@` suffixes. The label is displayed; use the target article's title unless the sentence needs other words. Wrap paths containing spaces in angle brackets. Update incoming links when renaming or moving files.
- Put a relationship in the link title: `[rg-dataplatform-prd](../cloud/rg-dataplatform-prd.md "hosted-in")`. The current article is the source; the linked article is the target. Names use letters, numbers, hyphens or underscores, without spaces. Untyped links create `links-to`; relationship titles are hidden during reading. OKF carries relationships in prose, so the sentence must still explain the connection.
- Place typed links in the main article prose at the point where the connection is explained. Do not append a relationship footer, a list of `See [...](... "type")` records, or generic “This is a … connection” sentences. Keep Topics/Tags at the bottom. Explain qualifications beside the relevant link; retain factual details without duplicating sentences. Keep data lineage (`reads-from`, `writes-to`) distinct from execution (`triggers`), structure (`hosted-in`) and dependency (`depends-on`). Preserve descriptions and operational status as prose. A configured connection does not establish successful execution. Do not invent targets, ownership, mappings or reciprocal relationships.
- Use `Tags: API, SQL, ETL` or `Topics: API, SQL, ETL.` as ordinary text. Both mean the same thing; graph nodes show the first three useful tags and ignore a trailing period. Preserve meaningful existing tags.
- Give each article Open Knowledge Format frontmatter when you create it, and add it when you substantially edit an article that lacks it: a leading `---` YAML block with a required non-empty `type` and, where the sources support them, the other OKF core keys `title` (matching the heading), `description` (one factual sentence), `resource` (the asset's canonical URI, never credentials or signed parameters) and `tags` (YAML list). Also write `created_at` when creating and refresh `updated_at` on every edit, as ISO 8601 timestamps with an offset; keep an existing `created_at`. Do not add `authors` or invent values. A frontmatter `title` overrides the heading as the display title. Preserve existing frontmatter keys. Do not add trailing YAML metadata, static IDs, serialized relationship blocks, or generated `## Connections` sections. Connections/backlinks are calculated from links. Ordinary HTTP(S) Markdown links are for external resources, not graph edges.
- Preserve concrete cloud, server, database and application identities exactly as the sources give them. Do not invent schemas, parameterized databases or missing mappings. Keep facts, inference, inactive configuration and unknowns distinct.
- Never change live infrastructure. Live read-only inventory needs explicit authorization. Exclude credentials, signed URL parameters, personal records and raw SQL module definitions. Articles must not depend on source exports, local input paths or tool instructions.

## Validate article changes

After every article create/edit, run the syntax checker against the applicable workspace. Pass changed files or a containing directory with `-Path`; omit it to audit the whole library:

```powershell
.\.agents\scripts\Validate-Knowledge.ps1 -KnowledgeRoot knowledge-example
.\.agents\scripts\Validate-Knowledge.ps1 -KnowledgeRoot knowledge-example -Path knowledge-example\infrastructure
```

The validator runs on Windows PowerShell 5.1+ without external modules. It checks balanced fences, Markdown article-link syntax, that targets exist and are written relative to the article (or `/`-bundle-relative), relationship titles, wiki links and `@@` suffixes, and that OKF frontmatter is closed and has a `type`. It does not judge factual accuracy or require frontmatter/IDs. Fix issues before delivery. `node scripts/validate-weave.mjs knowledge-example` also checks repository authoring conventions using the app parser.
