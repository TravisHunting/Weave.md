# Weave

Weave is a local-first Markdown workspace with typed links, a structural graph and chunk-based SQLite FTS5 search. [Open Knowledge Format](https://okf.md/) compatible Markdown files act as your source of truth. The underlying knowledge base is both agent and human friendly, with Weave as the optimal human interface into that knowledge.

Open Knowledge Format is a human and agent friendly markdown specification, released by Google in June 2026.

One application database holds graph/search/Kanban index data, workspace sessions and Git preferences.

## Why Weave?

Weave is similar to Obsidian in many ways. Both keep notes as plain Markdown files in folders you own and allow you to edit them to form a personal knowledge repository. 

Weave is aimed at professionals who want a polished interface for maintaining structured team knowledge, with the implicit understanding that agentic interfaces are the interfaces of the future when it comes to knowledge bases.

With Weave you can easily manage your personal knowledge bases alongside your team or organization knowledge bases without needing to swap tools. Weave allows you to index and search across all knowledge workspaces simultaneously.

Where the two differ:

- **Built around the Open Knowledge Format (OKF).** Links are ordinary relative Markdown links (`[Snowflake](../systems/snowflake.md)`) rather than `[[wiki links]]`, so a Weave library reads correctly in GitHub, VS Code, other Markdown tools and OKF-aware software without conversion. Optional OKF frontmatter (`type`, `title`, `description`, `resource`, `tags`) gives each article machine-readable identity. A library is portable by default, not tied to one application's conventions.
- **Typed relationships.** A link can say what kind of connection it is (`"writes-to"`, `"depends-on"`, `"hosted-in"`) in the standard link title, and the graph labels and directs those edges. It answers "what feeds this table?" rather than only "what mentions this note?", and the Connections panel lists incoming and outgoing relationships by type.
- **Git built in.** Source control is part of the app, with no plugin: per-workspace stage/commit, diffs, branches, stash, fetch/pull/push to several remotes, one-step sync, recently pulled files, and a visual merge-conflict resolver. Obsidian syncs required a paid plan, and any git integrations are community built rather than baked in.
- **Several workspaces in one window.** Different folders stay active side by side, each with its own colour, Files section and Git section. One tab can move between workspaces, and search ranks results across all of them. Obsidian opens one vault per window.
- **Relevance-ranked search.** Search uses SQLite FTS5 with BM25 ranking over passages (chunks) rather than whole files, with phrases, prefixes and exclusions, and shows the best-matching passage for each article. Deep search (Enter) gathers the strongest passages and the articles linked to them into an evidence view.
- **Friendly to AI agents and scripts.** Everything an agent needs is in plain files: relative links that resolve without the app, relationships stated in prose and link titles, a validator script, and authoring rules in `AGENTS.md` and a bundled skill. Deep search returns evidence with file paths, line ranges and source hashes, which a future model integration can consume directly.
- **Many visual settings without CSS.** Themes and individual colours, fonts and code fonts, fine-grained weight, line and row spacing, line numbers, tables, tab colours and file labels are all adjustable in Settings.
- **Share a whole knowledge base as one file.** **Export workspace** (the upload icon in the left rail) saves any workspace as a single read-only `.html` file containing every article, the relationship graph, search and the full Weave reader. Recipients double-click it and browse in any modern web browser: nothing to install, no account, no server, no internet connection, and nothing for them to break, because the export cannot be edited or pointed at other files. Attach it to an email, drop it on a file share or put it in a ticket as a snapshot of the docs at that moment. Alongside it, **Weave Lite** (`weave_lite.html`) is the same reader with no articles inside: open it in a browser, choose any Markdown folder, and read and search it with typed links and the graph, again with no install. In Obsidian, sharing is the paid, hosted Publish service; offline HTML export relies on community plugins.
- **A native Rust backend in a small download.** File access, parsing, indexing, search, graph traversal and Git orchestration run in compiled Rust with an embedded SQLite, rather than in JavaScript. The interface uses the WebView2 runtime already built into Windows instead of bundling its own copy of Chromium and Node.js as Electron apps (including Obsidian) do, so the whole app is a single portable executable, with no installer, plugins or runtime folder, and it starts quickly with a modest memory footprint.

Weave is aimed at shared, structured, version-controlled, agent-first knowledge bases, and is well suited for personal or team use in professional environments.

The primary desktop executable can also host browser access while you work locally: **Settings › Web server** starts, configures and stops it, with an optional background tray mode. Choose **This computer only** or **All network interfaces** (any address under Advanced); a browser origin is optional, and the running server's addresses appear as links. Select multiple known workspaces (active workspaces are selected initially); fresh browser tabs automatically open that selection. `Weave.exe server [options]` (Linux: `weave server`) runs without opening the GUI. Dedicated `weave-server` builds remain independent of Tauri and window-system libraries. See [the server guide](docs/SERVER.md).

## Use the portable app

Run **Weave.exe**. It contains the frontend, Rust backend and SQLite with FTS5; no Node executable or runtime folder is needed. Data defaults to `%LOCALAPPDATA%\Weave\.weave`, with a configurable location in Settings. Windows x64 and Microsoft Edge WebView2 Runtime are required. The build is unsigned.

**Linux and ChromeOS.** Install `weave_<version>_amd64.deb` (or `_arm64.deb` on ARM) on Ubuntu 22.04+, Debian 12+ or Linux on ChromeOS, or unpack `Weave-<version>-linux-x64.tar.gz` and run `./weave` on other distros with WebKitGTK 4.1. The interface runs in the system's WebKitGTK instead of WebView2; data defaults to `~/.local/share/Weave/.weave`. [docs/LINUX.md](docs/LINUX.md) covers requirements, ChromeOS, platform differences and how the Linux packages are built.

Choose **Open workspace folder…** in the W menu (or **Open** on the welcome page) and select any Markdown folder. Desktop Weave keeps several workspaces open side by side (up to 12): opening a folder adds another folder beside those already open, or switches to it when it is open already. Weave remembers the open workspaces, their order and every tab, and restores them on the next launch. It also restores the window size, position and maximized state; if a monitor has been disconnected, the window returns to a visible screen. Links, graph nodes and file selections navigate the current tab. Use Ctrl+T, the tab bar's **+** (a one-pixel divider separates it from **× All**), or right-click empty tab-bar space to open a new empty tab. Right-click an article in Files, or an article link in the article, Connections, search results or Deep search evidence, to **Open in new tab** (links also offer **Open link**). Drag a tab left or right to reorder the tabs; the order is restored with the session.

**Split view.** Two articles can be read side by side, as in VS Code or Obsidian. Right-click a tab for **Split right** (Ctrl+\\) to open its article on the other side, or **Move to right side** to move the tab itself; right-click an article in Files or an article link for **Open to the right**. From the right side these read **left**. Each side has its own tabs, **+** and **× All**, and each tab keeps its Back/Forward history and reading positions on either side. Drag a tab onto the other side to move it there, and drag the bar between the sides to resize them. Clicking a side focuses it: Back/Forward, Save, Source, the status bar, Files and new tabs follow the focused side, whose active tab keeps the accent colour. An article open on both sides shows the same text, and edits appear on the other side as you type; one save covers both. The graph sits above the article of the side it was shown from, and Deep search results cover the side they ran in. Closing the last tab of a side ends the split. Weave restores both sides, their active tabs and the focused side with the session. Each tab keeps its own Back/Forward history (Alt+Left/Right), which can move between active workspaces (articles of deactivated workspaces are skipped until reactivated), and remembers the reading position of each article in it, so Back, Forward and switching tabs return to the same place; workspaces remember open tabs, including empty ones. Close a tab with its ×, Ctrl+W, middle-click or its right-click menu. **Close all tabs** returns to the opening screen and stays empty when reopened. Opening an article reveals it in the indented Files tree when that pane is visible.

**Graph** in the title bar is an on/off switch, highlighted in the accent colour while the graph shows (the ◇ in the left rail does the same). The graph opens above the article at the height it last had, with one bar between them: drag the bar to any height, or drag it nearly shut to hide the graph entirely, bar included; Graph brings it back. With the graph showing, turning off **Show article** in the W menu gives the graph the whole pane and minimizes the article to a strip at the bottom; drag the strip upward or turn Show article back on to restore the shared layout. Turning Graph off restores the article automatically. An enlarged graph and article share a scrollable page, so the article keeps a useful reading area and the graph can scroll out of view. Scroll over the graph to zoom, or pinch with two fingers on a touch screen or touchpad; use its vertical scrollbar or drag to pan. The graph has no horizontal scrollbar. Controls float at its bottom left. Scroll over the article or use the far-right page scrollbar to reach the article beneath an enlarged graph. The divider follows the pointer without a minimum-height jump. The control bar shows depth, direction, Fit, Reset layout, Shuffle nodes and zoom; Visual styling › **Graph controls** can also show the note and link counts (with the zoom hint), the node spacing slider and the Colours button, which are hidden by default. Node spacing spreads layout positions apart without changing the zoom, and Shuffle nodes scatters the surrounding nodes semi-randomly around the centred current article, without overlaps, instead of in columns. The bar keeps an explanatory tooltip and keyboard label (arrow keys resize; Home hides the graph). Desktop neighborhoods are computed in Rust and arrive one depth layer at a time; later layers fade in and the view smoothly fits them, preserving existing node positions. Automatic layout uses at most five nodes per column, spreading larger groups horizontally. Nodes use the immediate parent folder for category/color, the first-line heading for their name (filename fallback), and up to three Tags/Topics in lighter text. Root articles use the workspace folder as category. Article/tab filename headings remain literal text.

The graph draws one arrow between each pair of notes, including pairs with relationships in both directions. A named relationship takes priority over `links-to`; when several named relationships connect the pair, the first one authored in the active article supplies the label and direction. If the active article supplies none, source filename and numeric source position provide a consistent choice. All original links remain available in Connections, traversal and evidence.

**Search** uses SQLite FTS5 in Rust to rank matching source chunks with BM25. Results show the best matching chunk for each article and link to its source line. By default every active workspace is searched and the results are interleaved by relevance; each compact card then names its workspace at the right of the title line and is bordered in that workspace's colour. A small **All workspaces** filter beside the result count ticks workspaces in or out (it appears only when several workspaces are active). **Search options** in Control panel choose whether search spans all active workspaces or only the workspace in use (the active tab's), whether cards show filenames (off by default) and how many preview lines they show (three by default). Press **Enter** for a **Deep search** of the workspace in use: it collects the best passages (1–5 starting matches, default 5) and, when **Include connected articles** is enabled, articles linked directly to them, up to a configurable maximum (default 20). It returns evidence without generating an answer. These preferences are remembered. Literal search phrases are highlighted in results and in the opened article.

Quotation marks request a contiguous phrase: `"customer relationship management"`. Unquoted terms must occur in the same chunk (or its title/path). Use `warehouse*` for a token prefix and `policy -draft` to exclude a term from matching chunks. FTS5 normalizes Unicode case and diacritics. Graph and text indexes update automatically; there are no models, downloads, semantic searches or index-management controls.

**Edit** is green when enabled and red when disabled (the Editorial skin uses a quiet outline instead). Read and Edit share one continuous CodeMirror document with identical row geometry: a single click places a prominent caret, including on empty lines and in document margins; selection can span paragraphs, and undo/redo operates across the whole article. Reading/editing toggles retain undo history, scroll position and line placement. Empty and populated body lines share stable font metrics and spacing, so typing starts at the caret without shifting following rows. Fenced code has an inset and subtly rounded corners. Fence rows share the code line height so the caret stays inside their background; clicking a hidden closing fence reveals it and places the caret after its backticks. Typing three backticks on a new line adds a closing fence on the next line; the caret stays after the opener for an optional language, and Enter creates the body between them. Backspace and Ctrl+Backspace preserve and visibly retain a preceding space until it is deleted explicitly. Typing # before bold or italic text inserts the Markdown heading separator automatically. Heading typography stays consistent with reading; text can sit immediately below a heading without a forced gap. The borderless editor uses the available pane width, including when the sidebar is collapsed. Links, relationships, bold, italic, <u>underline</u> (when enabled), strikethrough, ==highlights== and inline code reveal their source only when the caret or selection enters that construct; fenced code reveals its markers while editing inside the block. Unordered list markers render as bullets until the caret enters the marker. Backslash-escaped Markdown punctuation stays literal in reading and live preview. Ctrl+B toggles bold, Ctrl+I toggles italics, Ctrl+U toggles underline when underlining is turned on in Settings › Editing (off by default; underlines are written as `<u>…</u>` tags, which GitHub, VS Code and Obsidian also show, and with it off those tags stay visible as text), and Ctrl+K inserts a Markdown link around the selection (Command on macOS); Enter continues lists with a trailing space and preserves indentation. Tab uses four spaces, indenting list rows before their marker; Shift+Tab outdents even while a link suggestion is open, and selected rows indent together. Literal tabs preserve nested list structure in both reading and editing. Shift+Home includes hidden leading formatting markers on prose rows. On a list row it selects back to its text, leaving indentation, the list marker and any task checkbox outside the selection. Typing an asterisk, underscore, tilde, equals sign or backtick around selected text wraps the selection; repeated markers support bold, strikethrough and highlights. Obsidian-style `==highlights==` behave like bold for hidden markers, Home, Shift+Home and Ctrl+Backspace, and render as `<mark>` when reading. Underlines are written as `<u>text</u>`, the HTML that GitHub, VS Code and Obsidian already render; Weave treats the tags like bold marks (hidden until the caret enters, Home, Shift+Home, and Ctrl+Backspace removes a whole tag) rather than as raw HTML. Other HTML stays literal. All highlights share one colour, a display preference set in Visual styling › Reading & editing or by right-clicking a highlight while editing; articles keep plain `==text==`. Click a link to edit it; Ctrl+click follows it while editing, with a hover hint explaining the gesture. Pipe tables remain rendered while editing individual cells. Click a cell or focus the table and press Enter; Tab/Shift+Tab moves between cells, Enter moves down, Shift+Enter inserts a newline in the current cell, and Escape restores the cell value from when editing began. Drag header dividers left or right to resize adjacent columns; cell text wraps and rows grow to show all content, including during editing. Column widths are remembered on this device per workspace, article and table position. Cell line breaks are saved as Markdown-compatible `<br>` markers. Cell changes immediately update the same Markdown document, with shared undo and autosave. Right-click a cell to insert/delete rows or columns, move rows, align a column or sort its data alphabetically while preserving the header. A thin insertion control appears at a hovered row boundary. Right-clicking elsewhere in an article while editing opens an Obsidian-style menu: **Open in new tab** on an article link, spelling suggestions for a misspelled word, highlight colours for a highlight, **Add link**, **Format** (bold, italic, underline when enabled, strikethrough, highlight, code, clear formatting), **Paragraph** (bullet, numbered and task lists, headings 1–6, body and quote; choosing a line's current format returns it to body text), **Insert** (table, horizontal rule, code block) and Cut, Copy, Paste, Paste as plain text and Select all. **Paste** (and Ctrl+V) turns formatted clipboard HTML, from web pages, documents or Weave's own reader, into Markdown: headings, bold, italic, strikethrough, highlights, links, images, lists, task lists, quotes, code and tables (underlines only while underlining is enabled). Clipboard HTML without such formatting, such as code copied from an editor, pastes as its plain text, and nothing is converted inside code. **Paste as plain text** (Ctrl+Shift+V) always inserts the plain text. The desktop app reads the clipboard without asking for permission. Submenus open on hover or with the arrow keys. **Insert › Table** adds an empty two-column table (header, separator and one row) with the caret in the first cell; add rows and columns from the table's own menu. It is not offered when you right-click text you have selected. Table settings switch between visual cell editing and source-based editing, toggle insertion cues, and control automatic Markdown padding/separator formatting. With Automatically format tables enabled, table edits and saves pad each Markdown column to its longest source cell and extend separator hyphens to match, aligning the pipe characters. Save or Ctrl+S also formats an unchanged table in Edit mode. Turning this setting off preserves compact or manually spaced source. Opening an article, switching modes or navigating away does not reformat an untouched table. Cell contents and fenced examples remain unchanged. Source remains available for direct Markdown editing. **Source** shows the whole Markdown document in the same scrollable pane and is read-only unless Edit is enabled. **Autosave** runs after a 650 ms pause in typing by default. Control panel › **Editing** sets the pause in milliseconds, or saves only when leaving the article, or turns autosave off (then the floppy-disk button or Ctrl+S saves the open article and Ctrl+Shift+S saves every changed article). A tab whose changes stay unsaved for more than about a second (autosave off, a slow save, a failed save or a conflict) shows a white dot in place of its ×; ordinary autosaves never show it. Hover the dot to close the tab. With autosave off, unsaved changes stay with their article when you switch tabs or navigate, and Weave asks before closing a tab, deactivating a workspace, running Git or file operations, or closing the window with unsaved changes. Hidden emphasis and code marks take no space: inline code sits one ordinary space from its neighbours and reveals its backticks as soon as the caret is beside them, and Home moves to the very start of a line that begins with bold, italic or code. A link opens for editing as soon as the caret reaches either edge, so the arrow keys can enter it, and from the start of a line Up and Down move to the start of the neighbouring line, whatever markup it holds.

**Spelling.** Interface text uses American or British spelling (color/colour, gray/grey, minimize/minimise and so on) to match the system's English: American for the United States, British for other English-speaking regions and for non-English systems. Only Weave's own interface text is converted; article text, diagrams, file and workspace names and other content are never changed. While editing, misspelled words get a faint red wavy underline; Visual styling › **Spelling underline** sets its colour, opacity, thickness and style (wavy, dotted, dashed or straight), with a preview. Right-click one for up to five suggestions, ranked by closeness (a swapped pair of letters counts as one edit; all-caps acronyms come last unless you typed in capitals), and click a suggestion to replace the word, or choose **Ignore**. Control panel › **Spellchecking** turns checking on or off, checks prose and code (inline code and code blocks) independently (prose on, code off by default), and by default waits until a word is finished (a space or punctuation is typed, the caret moves away or the editor loses focus) before marking it, so half-typed words are not flagged; turn **Wait until a word is finished** off to mark words as you type. It also chooses the dictionary (follow the system, English (UK) or English (US)) and lists ignored words: add a word in the box, or remove one with × to check it again. In the Settings window the Spellchecking category also holds the Spelling underline controls. Link destinations, relationship names, HTML, comments, acronyms, mixed-case identifiers and words joined to digits or paths are never flagged. Only the visible lines are checked, so long articles stay fast. Checking uses [nspell](https://github.com/wooorm/nspell) with the Hunspell dictionaries from [dictionary-en and dictionary-en-gb](https://github.com/wooorm/dictionaries) (derived from SCOWL), embedded in the desktop app; Weave Lite and HTML exports are read-only and do not include them. Ignored words and spelling settings are kept on this device.

**Skins.** The **Skin** section at the top of Visual styling (and the Skin category in Settings) switches the interface between **Classic** (flat, square chrome), **Studio** (floating rounded panels, borderless controls, soft depth), **Compact** (a dense, square-cornered workbench with an activity-bar marker, underlined tabs and a status bar in the accent colour), **Editorial** (paper-coloured chrome, serif headings, hairline rules, outlined pill buttons) and **Aurora** (translucent panels over a gradient drawn from the accent colour, with blurred menus), plus riffs on them: **Aurora Thin** (Aurora with slim bars, tight margins, roomier tab titles and hairline glass scrollbars) and four skins whose active tab curves into the editor below as in a browser or Obsidian: **Studio Flow** and **Aurora Flow** (tabs on the window background above a floating article card), **Slate** (Compact's density with softened corners and a darker tab strip) and **Folio** (Editorial with outlined folder tabs). Every skin other than Classic styles the article scrollbar and the other scrollbars to match; the slimmer skins give the article roughly as much room as Classic. Each card shows a miniature in the current colours. A skin changes only shape, type, spacing and depth: it works with every colour scheme, leaves reading and editing settings alone and is remembered with the other appearance preferences; changing the colour scheme or switching light and dark keeps it, and **Restore defaults** returns to Aurora Flow and Lavender. Studio and Aurora draw the title bar on the background, so the Top bar colour applies to the other skins. Skins are plain CSS: `app/weave/skin-contract.css` defines the tokens a skin may change (radii, shadows, fonts, bar heights, row density, surfaces, dividers, icon stroke and motion) with Classic's values, and each other skin is one stylesheet in `app/weave/skins/` registered in `app/weave/skins.mjs`. A skin can extend another (Aurora Flow extends Aurora Thin, which extends Aurora) and then holds only its differences.

**Mermaid diagrams.** A fenced code block marked `mermaid` is drawn as a diagram (flowcharts, sequence, class, state, ER, Gantt, pie, mind map, timeline, Git graph and the other Mermaid types) in the article, Weave Lite, exports (unless left out when exporting) and Kanban card previews. The Markdown keeps the Mermaid source: nothing generated is written into the workspace, and the Rust backend treats the block as ordinary text. While editing, a diagram stays drawn until the caret enters it (click it, or move into it with the arrow keys); its source then appears with a live preview below that redraws as you pause typing, and a syntax error is shown in place. Mermaid is loaded only when an article shows a diagram, only diagrams scrolled into view are drawn, and drawings are reused for the same source and theme. Diagrams run no scripts or links (Mermaid's strict security level, shown as images). They follow the colour scheme, light or dark, and the skin's fonts and corners; **Visual styling › Diagrams** turns them off (blocks then show as code), turns the editing preview off, and chooses the colours (match the colour scheme, with an optional accent of its own; soft pastels; vivid; monochrome; or Mermaid's own default/dark themes), clean or hand-drawn lines, curved, straight or right-angled connectors, a card frame or none, fitting the article width or actual size, and centred or left alignment. Mermaid's own `%%{init: …}%%` directives and frontmatter in a diagram still apply to that diagram, except its security settings.

**Visual styling**, the palette icon in the left rail, starts with Aurora Flow and the Lavender theme. Its **Colours and Themes** section offers Light grey, Graphite, Warm paper, Sage, Ocean or Lavender, or customize individual interface colours with colour pickers. Save a custom colour scheme as a named theme and reload it later; while you edit a loaded custom theme's colours, its name stays in the **Theme name** box so saving updates it; schemes preserve colours separately from reading settings. Primary font, independent code font and code size, primary font size and weight (10-unit steps; because most installed prose fonts have only a few static faces, Weave adds a fine text stroke between faces so every step is visible, while variable code fonts change weight directly), line spacing and an optional article-width limit apply immediately to reading and editing. Line spacing defaults to 1.70, with no additional row padding. Code blocks have a separate spacing adjustment that adds to or subtracts from global line spacing, with a minimum effective value of 1.00. Code defaults to Cascadia Mono at 15 px. Other code fonts include Consolas, Cascadia Code, Courier New, Lucida Console, Fira Code, JetBrains Mono and Source Code Pro; unavailable fonts use local fallbacks without downloading anything. Additional row spacing applies consistently in both modes, including blank rows. Article indent controls the left padding that holds the line numbers. Ctrl+scroll over the article or Source scales prose and code by the same zoom percentage, preserving their independent base font sizes; the Reading & editing section also provides a zoom slider and reset. Table controls set cell padding, grid/row/no borders, border thickness, a separate border colour, header tint and alternating rows. Borders default to 2 px with higher contrast than other interface borders, and alternating row shading defaults to on. The top bar has its own colour control under Colours and Themes. These controls appear in both the Visual styling sidebar and the floating Settings window from the same definitions. Discreet source-line numbers appear in both modes at 50% opacity by default; choose Read, Edit, Both or Off and adjust their colour, opacity and font size (7–20 px, default 9 px). Numbers are centered horizontally in the article indent. Vertically, each number is centred on the first rendered text line, including headings, prose, code, wrapped source lines and Source view at any font size or zoom. Positions are re-measured when rows are rebuilt, the content resizes or fonts finish loading. Wrapped continuations and rendered table cells do not invent extra source-line numbers. Colour, file sidebar, reading/editing, code, line-number and table sections start collapsed with compact spacing. The article scrollbar and thumb remain visible without hovering, independently of the border colour. The article scrollbar holds its grip under the pointer while offscreen row heights are measured, including on the first drag through a long article. Preferences are remembered on this device; **Restore defaults** resets the active appearance while retaining saved colour schemes. The half-circle button switches between light grey and graphite without changing reading settings.

**Title bar.** By default the tabs sit in the title bar itself, as in a web browser, so the article gains a whole bar of height: the article column runs to the top of the window, the sidebars start below the tab row, and the title bar's controls float at either end of that row. At the start are the **W menu**, Back and Forward; at the end are **Graph**, the right-sidebar toggle, **Edit** and **Source** (switches the active article between the formatted view and its Markdown source, like **Source mode** in the W menu). Tabs never pass under these controls, including with a collapsed sidebar or in split view, where each side's tabs share the row. Turn off **Show tabs in the title bar** (Visual styling › Tabs) for a separate title bar above the tabs; the **Top bar** colour applies to that layout. The W menu holds **Open workspace folder…**, **Save** (Ctrl+S), **Reload from disk**, **Source mode**, **Show article** and **Settings…** (Ctrl+,); arrow keys move through it and Escape closes it. The status bar at the bottom shows the save status, the bold workspace path (with its colour dot when several workspaces are open) and the active article's relative path (Windows paths use backslashes consistently), followed by the article, link and broken-link counts in singular or plural as appropriate. Desktop windows use custom minimize, maximize/restore and close controls at the right end of the title bar; drag any empty part of the title-bar row (beside the tabs or above the sidebars) to move the window, or double-click it to maximize/restore.

**New folder** and **New article** are centered in the Files heading, with **Collapse all folders** (every workspace) beside them; each workspace heading has its own collapse button, also offered when right-clicking a workspace heading, a folder or blank space. Folder chevrons align vertically with their names. Click the empty space below the file tree to select the workspace root for creation; the open article remains visible. Right-click a folder to create inside it, or the empty space below the tree to create at the workspace root. Creation asks for a name only, adds the hidden `.md` extension, and supplies a first-line heading to new articles. Ctrl+N opens New article at the workspace root, enabling Edit if needed. Desktop Files and changed Git entries offer **Show in explorer** for files and folders; deleted entries reveal their nearest surviving parent. Right-click a file or folder to **Copy** it (or press Ctrl+C in Files), then right-click a folder, a file or blank space and choose **Paste** (or press Ctrl+V) to write a copy there; the copy is byte for byte, and a name already taken gains “copy” (`Notes copy.md`, `Notes copy 2.md`), as does a board whose filename another board has. A folder is not pasted inside itself. Within a workspace files and folders of any type are copied; into another active workspace, articles only. Right-click a file to **Rename file** or **Move**; F2 opens Retitle Article for Markdown files; folders and other filetypes retain Rename. Markdown rename fields hide and preserve `.md`; folders explicitly say **Rename folder**. With Edit enabled, drag a file or folder onto another folder (or onto a file to use its folder), or onto a workspace heading or blank space for the root, to move it; hovering over a closed folder opens it, the pane scrolls near its edges and Escape cancels. Moves stay within a workspace. The link-update confirmation appears only when existing links are affected (a move with none happens at once), and defaults to updating them: Enter or Space always means **Yes**, so not updating links (**No**) needs a click; Escape or **Cancel** leaves everything in place. **Retitle Article** changes the first-line heading, or adds one when absent, and also updates an OKF frontmatter `title` when present, while preserving the filename and incoming links. Delete is available in the context menu and asks for confirmation; it never asks you to save first. By default deleting removes the file from disk, and you rely on Git or your own backups; **Keep a backup copy of files deleted in Weave** under Settings › Storage location copies each deletion first and shows where.

Clicking an active left-rail panel icon hides its sidebar; clicking again reopens it. Its divider follows the pointer all the way to the rail; released there, the pane hides and reopens at its previous width. The header's right-sidebar toggle opens a second sidebar, which remembers its chosen panel, width and open state. Dragging its divider to the right edge closes it completely and preserves its prior width for reopening. Either side can show Files, Search, Source control, Visual styling or Control panel. Each panel has one instance: selecting a panel already visible on the other side swaps the panels while retaining their inputs and state.

Control panel hides dot-prefixed folders by default. Right-click any folder to **Hide folder**, or right-click the Files heading or blank space below its tree to toggle **Show hidden folders**. The Show hidden folders menu label aligns left, with a checkmark on the right when enabled and an X when disabled. Visible hidden folders are dimmed, and an explicitly hidden folder can be unhidden from its context menu. Folder choices and the visibility toggle are remembered per workspace and work in either sidebar, including read mode. Hiding changes only the Files view; article links, search and indexing remain available. Private/generated directories such as `.weave` and `.git` remain excluded from browsing and indexing regardless of this toggle.

**Multiple workspaces.** Each open workspace has a name and a colour. The name defaults to the workspace's root folder name and the colour to a random colour no other workspace uses. With several workspaces open, Files lists each workspace's tree under a small coloured heading, with a horizontal bar between workspaces; click a heading (or blank space in its section) to select that workspace's root for creation. Tabs from different workspaces can be open together: each tab is coloured in its workspace's colour and shows the workspace name in small text at its bottom edge, without making the tab taller. Tab titles are bold. A tab keeps one workspace's history, so choosing an article from another workspace opens it in that workspace's most recent tab, or a new tab. New tabs and Ctrl+N use the workspace in use (the active tab's). Right-click blank space in Files to deactivate a workspace.

The **Workspaces** section at the top of Control panel (and Settings) lists open workspaces as coloured cards showing the path, article and tab counts, and which is **In use**: the workspace of the active tab, which deep search, new tabs and Ctrl+N use. It updates as soon as another tab or article becomes active. Rename a workspace (leave the name empty to use its folder name), pick its colour, move it up or down to reorder Files and Source control, or **Deactivate** it. Deactivating hides the workspace, its tabs, Files and Source control section and stops watching it, but keeps its session: **Inactive workspaces** lists it with an **Activate** button that restores its tabs without the folder picker, and the opening screen offers the same list. **Show workspace names in tabs** turns the small workspace name in each tab on or off; tabs keep their workspace colour either way. Visual styling › **Tabs** also turns tab colouring off or sets its opacity.

```text
[Azure Data Factory](../systems/azure-data-factory.md "writes-to")
[Snowflake](./snowflake.md "depends-on")
[Data Platform team](<../teams/Data Platform.md>)
[Overview](/overview.md)
```

Article links are standard [Open Knowledge Format](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md) Markdown links to a `.md` file, so they also work in GitHub, VS Code, Obsidian and other Markdown readers. Weave writes paths relative to the linking article, always starting with `./` or `../`. It also reads OKF bundle-relative paths that start with `/` (resolved from the workspace root). A bare path such as `systems/db.md` is read relative to the article, then from the workspace root; the validators ask for a `./` or `../` path instead. Wrap paths containing spaces in angle brackets.

A relationship type goes in the standard link title: `[Snowflake](./snowflake.md "depends-on")`. A title that is a single name (letters/numbers, hyphens or underscores) types the link; any other title is an ordinary tooltip, and untyped links use `links-to`. Other Markdown readers show the type as a hover tooltip; OKF itself carries relationships only in prose, so keep explaining the connection in the sentence. The type is hidden in normal article, search and evidence rendering and visible while editing or in Source. Graph/Connections UI derives relationships from these links. The authored label is displayed; an empty label `[]` shows the target's title. Ambiguous or missing targets stay visible as broken links. HTTP(S) links and links to other file types are ordinary links, not graph edges. Renaming or moving an article rewrites incoming links and the moved article's own relative links, keeping each link's relative or `/` form.

Linking works like Obsidian. Typing `[` inserts the closing `]` and opens the article list immediately. The list filters as you type (every typed word must appear in the filepath or title), and arrows plus Enter/Tab choose an article. Choosing one replaces `[query]` with `[Article title](./relative/path.md "links-to")`, naming the relationship so it is clear what to change. Escape, Right arrow or clicking elsewhere closes the list. The editor also pairs `{`, `` ` ``, `"` and `'`: typing the closing mark steps over it, Backspace between an empty pair removes both, and a quote or backtick touching a word (such as an apostrophe) stays single. Three backticks still open a fenced code block.

Articles may start with OKF YAML frontmatter. `type` is required; `title`, `description`, `resource` and `tags` are the other core keys:

```yaml
---
type: BigQuery Table
title: Orders
description: One row per completed customer order.
resource: https://console.cloud.google.com/bigquery?p=acme&d=sales&t=orders
tags: [sales, revenue]
---
```

Read and Edit modes hide the frontmatter, and line numbers continue to count its lines; Source mode shows it. A row of property pills above the first line shows Type, Title, Description, Resource and Tags, followed by any other frontmatter fields except the `weave` block (Kanban placement), which Weave maintains and Source mode shows. In Edit mode you type directly into a pill: Enter or leaving it saves, Escape restores it, and Tab moves to the next pill. Clearing a pill removes its field, except the required `type`. Each tag is its own `#tag` pill (the `#` is not stored in the YAML); **+ Tag** opens a tag pill, Enter adds it and opens the next, and clearing a tag removes it. Other keys already in the frontmatter appear as editable pills and accept YAML flow values such as `[a, b]` or `{by: name}`. Unknown keys and comments are preserved. An article without frontmatter shows **+ Add OKF properties**; clicking it replaces the button with the pills (`type: Note` plus a title from the first-line heading), and puts the caret in Title when there is no heading. A frontmatter `title` replaces the heading as the display title in Files, the graph and links; frontmatter `tags` lead the graph tags. New articles start with `type: Note` and a title matching the filename and generated heading.

Weave also records two timestamps, local ISO 8601 times with their UTC offset (`2026-10-07T14:03:22+13:00`). Every save in Weave sets `updated_at`; `created_at` is added once, from the file's creation time, and kept afterwards. An article saved without frontmatter gains a block with `type: Note` and both timestamps. Renaming or moving an article updates `updated_at` in the articles whose links it rewrites. Neither field has a property pill, since they are not meant to be edited by hand, but Source mode shows and edits them like any other YAML. Articles that are never saved in Weave are left unchanged, and frontmatter that is not valid YAML is never stamped.

The gear below the Control panel icon (or Ctrl+,) opens a Settings window in the style of Obsidian. Categories are listed on the left: the Control panel sections under Options and the Visual styling sections under Appearance. The search box filters individual settings across every category. These are the same controls as the sidebars, which show a note while the window is open.

Ctrl+O opens any Markdown file on the computer, starting in the root folder of the workspace in use; a file inside an active workspace opens as that workspace's article. Other files, and Markdown files dragged from File Explorer onto the window, open in a new tab marked ↗. Ctrl+F opens Weave's find bar, which searches the whole open article, sits at the top right of the article pane and steps through matches with Enter and Shift+Enter. Control panel › Editing can switch Ctrl+F to the WebView's own find bar, but that bar sees only the lines drawn near the screen (Weave renders long articles incrementally to stay fast), so it misses text further away. These files stay outside the workspace: they are not indexed, searched or graphed, their links are not resolved against the workspace, and their tabs are not restored with the workspace session. On the desktop, Weave can read and save only the files you chose or dropped, keeping their line endings. The browser reader opens them read-only.

**Visual styling** contains the file-label settings. Labels default to **Title - Filename**, with a filename fallback when a heading is absent; alternatives show either label alone or both in the other order. Secondary labels align against the right edge by default, with a toggle to keep them beside the primary label. The primary label keeps priority for the available width. Control panel retains the visible-extension and all-filetype switches. Hover a row to see both labels and its path. Non-Markdown files can be organized but are not read or indexed as articles; private/generated folders remain excluded. First-line headings are optional syntax but important for reader navigation: update the title while keeping filepaths stable.

Articles need no IDs or explicit Connections section; OKF frontmatter is optional. Put typed links directly in the main prose where the connection is explained; do not append separate relationship statements after the article. `Topics: API, SQL.` and `Tags: API, SQL` are equivalent; trailing periods are ignored. Tags on multiple lines combine without duplicates.

**Kanban boards.** A board is any article whose OKF frontmatter has `type: Kanban Board`; it can live in any folder. Its columns, in order, are listed in the board article itself, each with a stable `id` and a displayed `title`:

```yaml
---
type: Kanban Board
title: Development Board
weave:
  kanban:
    columns:
      - id: backlog
        title: Backlog
      - id: in-progress
        title: In Progress
      - id: done
        title: Done
---
```

Any article becomes a card by naming the board in its own frontmatter; the article stays the card's content and identity, and nothing is copied elsewhere:

```yaml
weave:
  kanban:
    board: Development-Board.md   # the board's filename (or a ./, ../ or / path to it)
    column: in-progress           # a column id of that board
    rank: 2000                    # order within the column, lowest first
```

Board filenames must be unique among the workspace's boards (an ordinary article may share a board's filename; only articles with `type: Kanban Board` are boards), so a card can name its board by filename and keep it when the board moves between folders; renaming a board's file updates the cards that name it (with the link-update prompt, which then also counts Kanban cards). Weave refuses to create or rename a board onto an existing board's name, and boards that share a filename anyway (created outside Weave) are flagged in the Kanban sidebar and on the board; cards naming that filename wait under **Needs attention** until one board is renamed. Opening a board article shows the board: columns in board order, cards ordered by `rank` (cards without a rank last), each with its title and, optionally, description, tags and folder. Drag a card within a column or to another column (or use Ctrl+arrow keys on a focused card); Weave writes only that card's `column` and `rank` (with `updated_at`), choosing a rank between its neighbours (2000 and 3000 give 2500). When no readable rank is left between two cards, only that column is renumbered 1000, 2000, 3000…. Cards whose column id is not on the board, that have no column, or whose board filename is shared stay visible in a **Needs attention** lane at the start of the board, exactly as written: drag one to a column, or right-click it, to correct it. Weave never adds a column because a card names one. Cards naming a board that does not exist are listed in the Kanban sidebar under **Cards with an unknown board**. Right-click a column heading (or use its ⋯) to add a card, rename the column (its id, and so its cards, stay the same), add a column after it, move it left or right, or delete it (a column with cards offers to move them to its neighbour first). **+ Add card** creates a new article in the board's folder (or in a folder named after the board, in Settings). Right-click a card to preview or open it, move it to a column, to the top or bottom of its column or to another board, remove it from its board, show it in Files or delete it. Drag an article from Files onto a column to add it there as a card: Weave writes its `weave.kanban` board, column and rank (adding OKF frontmatter with `type: Note` when the article has none); an article already on the board moves, and a card of another board moves to this one. This works without Edit unless Settings › Kanban requires it, and only for boards of the article's own workspace. **Article** shows the board's article; **Show board** returns. **Source** shows the board's raw Markdown like any article's; **Show board** leaves Source.

Clicking a card shows it in the right sidebar's **Card** panel: its title, path, description and tags, its rendered text with working links, Board and Column choices to move it, and buttons to open it beside the board, in a new tab or in place (Ctrl+click opens it in the tab instead; Settings › Kanban can make that the default). The **Kanban** sidebar (the columns icon in the left rail, whose badge counts cards needing attention) lists each active workspace's boards with card and attention counts, duplicate board names and cards with an unknown board, and has **New board**. In Files, boards have a board icon; right-click a folder (or blank space) for **New Kanban board here…**, an article for **Add to Kanban board…** (choose the board and column), a card for **Show on Kanban board**, **Preview card** or **Remove from Kanban board**, and a board for **Open Kanban board** or **Open board as article**. Settings › Kanban chooses what clicking a card does, whether moving cards needs Edit (by default cards move whenever the workspace is writable), the columns of new boards, where new cards are created, what cards show and the column width. Weave Lite and exports show boards read-only.

**Source control**, beneath Graph in the left rail (Refresh sits above Visual styling), has one expandable section per open workspace, in workspace order, each with that workspace's Git controls and pending-file count. A single workspace's section opens by default. When an article becomes active in a tab, its workspace's section expands and the others collapse. It shows staged, unstaged, untracked and conflicted files, diffs (side by side by default, with a unified option), commit history, branch and upstream status, and selected remotes. Stage/unstage individual files or all changes, commit staged changes (Ctrl+Enter), create/switch branches, stash/apply tracked changes, initialize a repository, add a remote, fetch, pull or push. **Commit all & sync** stages and commits all changes with your message, fetches and merges incoming changes, then pushes to every checked push remote. **Remote management** lists remote names and URLs, adds remotes inline, and remembers multiple push targets per repository. Fetch/Pull selects the single remote used for incoming changes. Pushes run sequentially; a failure reports which remotes succeeded and leaves local commits intact. A clean workspace can sync without another commit. Conflicts stop the push and retain local commits. Choose **Resolve** beside a conflicted file to compare current and incoming versions, choose either side or both for each conflict block, and edit the combined result. **Save draft** keeps an unfinished resolution; **Save & stage** marks a completed resolution ready to commit. Whole-file choices also support binary files and accepted deletions. Stale resolutions are rejected if the working file or conflict index changed, and unresolved markers cannot be staged. Commit or sync again after resolving every file; merges with no remaining file differences can still be completed. Files over 1 MB, linked files, submodules and directory conflicts require an external Git client, as does continuing an externally started rebase. The separate **Pull** action remains fast-forward only. **Recently pulled files** retains the last five pulls/syncs that brought in changes, with timestamps and diffs for up to 200 files per pull, including additions, renames and deletions. This history is stored per repository in the native backend; pulls performed in another Git client are not recorded. Tracked-file discard asks for confirmation and restores unstaged changes. Weave saves the current article before Git actions, preserves drafts if files change during an operation, and refreshes the workspace afterward, including after a merge conflict. Private `.weave` runtime data is excluded from staging and commits. Open the repository root to manage Git; subfolders point you to that root. Git must be installed separately and authenticated using your system credentials; Weave does not bundle Git or collect credentials.

The left Source control icon shows a small count of unique pending files across open workspaces, including local changes and files changed in unpushed commits. It refreshes while the panel is closed. Desktop **Show in explorer** selects the exact file in its containing folder, including paths with spaces or commas. **Show hidden folders** appears only on folder and blank-space Files menus.

**Edit .gitignore** in Source control opens the repository-root ignore file, or creates it on save when absent. Saving preserves its encoding and newline convention, rejects external changes while the editor was open, and does not stage or commit it.

The Source control panel puts Sync, Commit, Stage all, Unstage all, Push, Pull, Fetch and Refresh in a compact icon toolbar with hover labels. A single-line commit message defaults to the current ISO timestamp above the changed-file list. Replace it with a custom message at any time; Commit and Sync use this field without a message popup. Branch and remote controls follow it. Discarding an untracked ordinary file requires a separate deletion confirmation because Git cannot recover an uncommitted file. It deletes only that selected file after verifying that it remains untracked and unchanged; folders and linked files are excluded. Tracked-file discard continues to restore unstaged changes.

## Export a portable workspace

**Export workspace** (the upload icon in the left rail, also under Settings › Export) saves a workspace as one read-only HTML file. Choose the workspace when several are active, then **Export…**; the save dialog suggests `{workspace name}.html`, with spaces replaced by underscores, in a folder of your choice. Unsaved drafts in that workspace are offered for saving first, because the export reads the files on disk. **Draw Mermaid diagrams** (on by default, remembered on this device) includes the Mermaid renderer, about 3.4 MB, only when an exported article contains a Mermaid block; exports without diagrams, or made with the option off, leave it out and show Mermaid blocks as code.

Right-click a workspace heading or blank space in Files for **Export workspace as HTML…**, or a folder for **Export folder as HTML…**, which exports only that folder and its subfolders (named after the folder; links leaving it show as unavailable). The file is the same reader as Weave Lite with the articles, folders and graph embedded, and it opens articles with the graph pane showing so first-time readers see it, with the narrowest Files panel and file extensions shown (readers can change both): Files, tabs, Back/Forward, the graph, Connections, search, Deep search over the text and all Visual styling work in any modern browser, offline, with no network requests. It cannot open other folders or files and nothing in it can be edited; only editing the `.html` itself changes it. Options can leave out the relationship graph (hiding Graph and Connections) or the list of non-Markdown files. Readers keep their own appearance preferences in their browser.

## Application data

On Linux the folder below is `$XDG_DATA_HOME/Weave/` (normally `~/.local/share/Weave/`).

```text
%LOCALAPPDATA%/Weave/
  location.json                 # only when a custom data location is selected
  .weave/                       # default application data folder
    weave.sqlite                # one database for every registered workspace
    weave.sqlite-wal / -shm      # SQLite transaction files while running
    native.lock                 # OS lock, released automatically on process exit
    window-state.json
    webview/
    operations/                 # rename journals
    trash/                      # only if delete backups are enabled; never pruned
```

Open workspaces are watched, scanned and searched; Deep search uses the current workspace. Closed workspaces retain their cached rows and sessions in the same database. Control panel preserves file visibility and per-workspace **Workspace refresh** settings (choose the workspace beside them when several are open): native file-change detection, periodic refresh (300 seconds by default), an interval of 10–86400 seconds, and metadata or full-content comparison. Saves update graph and search rows immediately. Changes made outside Weave are applied for just the files the watcher reports; the periodic scan is a safety net that reads only files whose size or modification time changed. Refresh explicitly checks file contents.

**Choose location** in Settings selects a parent folder for the complete `.weave` data directory. Weave creates `.weave` there on the next launch, before opening the window, and copies the database, WebView profile, window state, settings and recovery files. The selected parent must exist and its `.weave` child must be absent. It must be separate from the current data folder and outside Markdown workspaces. Weave verifies the copy and leaves the previous folder as a backup. A small `location.json` pointer under `%LOCALAPPDATA%\Weave` records the custom location; the default needs no pointer. Locks prevent two running copies from sharing a data folder.

Graph and search rows are rebuilt from Markdown into `weave.sqlite` whenever needed. Keep `weave.sqlite`: its graph and search rows are disposable, but it also contains durable sessions and preferences.

Deletes require confirmation. They are permanent by default; with delete backups enabled, each deletion is first copied, with a `restore.json` naming its workspace and path, to its own folder in `trash`, which is never pruned. Rename/move previews count affected article links; accepting updates only destination spans and preserves authored labels, relationships, encodings and line endings. Stale previews and saves are rejected. Failed multi-file operations roll back when safe and retain a journal for manual recovery. These operations and data-folder relocation are recoverable, not crash-atomic.

## Develop and build

**Self-hosted web application.** Weave also has a single-user headless server using the same Rust core and editing interface. Run `docker compose up -d --build` and open `http://localhost:8765`, or build with `npm run build:server:native` and run `weave-server --host 127.0.0.1 --port 8765 --workspaces ./workspaces --data ./.weave-server`. Workspaces remain independent, and browser tabs keep separate navigation. [docs/SERVER.md](docs/SERVER.md) covers filesystem grants, persistent volumes, limitations and protected remote deployment. Built-in administrator authentication uses Argon2id passwords and expiring browser sessions, with optional Cloudflare Turnstile. First headless startup provisions credentials once; desktop Server Settings and local CLI commands manage them. Remote deployment requires HTTPS at a reverse proxy or tunnel.

Use Node.js 24+ (for built-in SQLite), npm, Rust MSVC and Visual Studio C++ build tools. Dependency installation may use the network; builds and tests run offline once dependencies are installed.

```powershell
npm ci
npm run build
npm run build:desktop
npm run prepare:runtime
npm run build:test-host
npm test
cargo check --offline --manifest-path src-tauri/Cargo.toml
cargo test --offline --manifest-path src-tauri/Cargo.toml
cargo build --offline --manifest-path src-tauri/Cargo.toml --features custom-protocol
npm run test:runtime
```

Prefer debug builds for development and testing:

```powershell
.\scripts\Build-Debug.ps1
.\src-tauri\target\debug\weave.exe
```

The script can be launched from any working directory. It builds the desktop shell, validates embedded assets, runs an offline debug build and prints the executable path (respecting `CARGO_TARGET_DIR`). For constant development, `.\scripts\Build-Debug.ps1 -Quick` (`npm run build:quick`) adds about 15–25 seconds of checks: `npm run test:quick` (the unit tests without the Git workflows, the Rust test host, the PowerShell validator and a few multi-second tests; listed in `scripts/test-quick.mjs`) before the Rust build, then `verify-native.mjs --quick`, which launches the new executable twice for startup, graph streaming and CRUD/FTS5 but skips window restoration, the desktop-hosted server and data relocation. Quick checks are not a release gate; run `npm test`, `cargo test` and the browser suites before relying on a change. No runtime folder is required. Release packaging is reserved for distribution: it builds a portable executable and verifies it with an empty PATH, and places a freshly built `weave_lite.html` beside `Weave.exe`. That verification drives the packaged executable through Playwright, a pinned devDependency installed by `npm ci`, with installed Edge; the script checks for it before building. `-SkipChecks` skips the tests and this verification.

```powershell
npm run package:windows
# Prepare dependencies explicitly if needed:
.\scripts\Package-Windows.ps1 -PrepareDependencies
# A folder-only package avoids creating a large zip:
.\scripts\Package-Windows.ps1 -NoZip
# A trial release with the abridged checks of Build-Debug.ps1 -Quick (not for distribution):
npm run package:windows:quick
.\scripts\Package-Windows.ps1 -QuickChecks -NoZip
```

Linux packages (`.deb` and `.tar.gz`, amd64 and arm64) are built reproducibly in the WSL distro `Ubuntu-22.04` by `npm run package:linux` (add `-- -Arm64` for ARM). `npm run package:all` builds the Windows package and then the Linux amd64 and arm64 packages from the same working tree, stopping at the first failure; `-SkipChecks`, `-SkipArm64`, `-SkipLinux` and `-NoZip` are passed through. [docs/LINUX.md](docs/LINUX.md) records the build machine setup (`scripts/linux/setup-build-env.sh`), the pinned toolchain and the Linux tests.

Browser verification uses Playwright (a pinned devDependency, installed by `npm ci`; `WEAVE_PLAYWRIGHT` can point at another copy) and installed Edge:

```powershell
npm run test:browser
npm run test:dynamic
npm run test:desktop
npm run test:git
npm run test:editor
npm run test:tables
npm run test:mermaid
npm run test:layout
npm run test:graph
```

Screenshots are written under `test-results/`. The editor suite covers blank-line clicking, caret visibility, undo isolation, paragraph navigation and input-to-frame measurements on a 1,000-paragraph article; timings are informational and machine-dependent. The Git suite exercises diffs, commits, branches, stash and remote operations against disposable local repositories. On Linux the same test drives the app through WebKit's WebDriver on a private virtual display (`bash scripts/linux/with-display.sh npm run test:native -- <path-to-weave>`). Desktop verification uses real services with native IPC/folder selection supplied by the test harness. ### Scale benchmarks and performance budgets

Weave is built to stay responsive with hundreds of thousands of articles; [PERFORMANCE.md](docs/PERFORMANCE.md) describes the design, the budgets and measured results. Two benchmarks generate realistic vaults (folders, OKF frontmatter, typed links, tags, Kanban cards) under `%TEMP%\weave-scale` (reused between runs; `--cache DIR` moves it) and drive the release-profile Rust backend:

```powershell
npm run bench:scale -- --docs 100000            # backend: cold/warm start, reads, search, writes, reindex responsiveness, memory
npm run bench:scale -- --docs 500000 --check    # fails when a budget in scripts/performance-budgets.json is exceeded
npm run bench:ui -- --docs 100000 --check       # the desktop page in Edge: restore, typing, search, Files, external changes, heap
```

Results are written to `test-results/scale-benchmark-<docs>.json` and `test-results/ui-benchmark-<docs>.json`, including the backend's `metrics` (request latencies, walk/compare/parse/write timings). Generating a 500,000-article vault (1.25 GB) takes about 25 minutes once; indexing it takes several minutes in the background.

For an informational search benchmark, run `npm run build:test-host` then `node scripts/benchmark-native-search.mjs`. It generates 1,000 articles (6,000 chunks), measures warmed Rust search requests including test IPC, and removes its temporary workspace. The Windows debug run measured about 0.8 ms p95 for a selective term and 46 ms p95 for a broad two-term query; timings depend on hardware, corpus and build profile. Results are saved in `test-results/native-search-benchmark.json`.

The Kanban suite (`test:kanban`) drags cards within and between columns against the Rust backend and checks the written frontmatter, the Needs attention lane, the card preview, column editing, Files menus and duplicate board names under the packaged CSP; `npm test` also checks that Rust and the browser reader derive identical boards. Table verification covers cell editing, undo, keyboard navigation, structural actions, sorting, safe rendering, formatting preferences, persisted column resizing, wrapping, growing inputs and multiline cells. The optional `npm run test:native -- src-tauri/target/debug/weave.exe --explorer` check also opens Explorer for an isolated nested test file and verifies its selection. Desktop checks also save visual table edits to disposable files and reload them. Layout checks measure line-number glyph alignment and verify equal prose/code zoom in article and Source views. The phone suite (`test:mobile`) emulates a touch phone on a plain-HTTP origin (no `crypto.randomUUID`) and checks the drawers (Files open at start), touch sizes, the tab bar that slides away while reading, pinch zoom in the graph, Back handling, the Settings sheet and the return to the desktop layout.

## Browser readers

`npm run build` creates **Weave Lite**, `weave_lite.html`: the standalone read-only reader with no articles embedded. It starts empty and opens a local Markdown folder through the browser's folder picker. It never bundles a `knowledge/` folder; to share a library with its articles inside, use **Export workspace** in the desktop app, which fills the same reader page with one workspace's articles and graph. `npm run build:desktop` also writes `dist/export-template.html`, that reader page with a data placeholder, which the Rust build embeds in the executable for exporting. The supplied `knowledge-example/` library is a fictional, company-agnostic data platform written in the current authoring format (OKF frontmatter, relative Markdown links with typed relationships in link titles, Mermaid diagrams). It is not opened automatically.

Standalone HTML makes no requests and is read-only. It derives a graph in memory from the same link parser; desktop structural queries use SQLite. The dynamic preview is also read-only and binds only to loopback:

```powershell
npm start -- --workspace C:\Notes
```

Dynamic mode permits only its same-origin knowledge API. Editing and native FTS5 search are available in the desktop app and Weave Server. The dynamic evidence view uses local text matches.

On a phone, or any window narrower than 760 px (and phones held sideways), every reader uses a phone layout: the article fills the screen, the rail and Files sidebar slide in from the title bar's ☰ button (and are open at start when no article is shown, so the workspace is in view at once), the right sidebar slides in from the other side, tabs scroll sideways in their own row, which slides away while you read down the article or type and returns when you scroll back up, split view shows only the focused side, Settings becomes a full-screen list of categories, and the browser's Back closes an open dialog, menu or drawer before going Back in the tab. `knowledge-example/` is a fictional, company-agnostic data platform (a subscription retailer's warehouse, pipelines, Azure infrastructure, reporting, projects, suppliers and teams): 46 articles with OKF frontmatter, 339 resolving filepath links (270 typed) and 51 Mermaid diagrams across 14 diagram types. Every name, host and figure in it is invented; resource URIs use the reserved `example.com` domain. Typed links are integrated into the main prose. Run `.\.agents\scripts\Validate-Knowledge.ps1 -KnowledgeRoot knowledge-example` for the standalone syntax check, and `node scripts/validate-weave.mjs knowledge-example` for additional repository conventions. AGENTS.md and the author-knowledge skill describe the authoring format.

## Architecture and limits

Tauri commands execute Rust services directly. Workspace scope and logical resource grants prevent stale operations from targeting another workspace. Rust owns safe file operations, watching, the unified SQLite database, chunk retrieval, Git execution and sessions. The frontend owns rendering and device appearance preferences. Native graph neighborhoods stream through Tauri Channels. See [WEAVE_ARCHITECTURE.md](docs/WEAVE_ARCHITECTURE.md) and [PERFORMANCE.md](docs/PERFORMANCE.md).

Interface responsiveness does not depend on indexing, Git or workspace size. Requests run concurrently without a global lock: reading, searching and saving use pooled database readers or short per-workspace locks, so a full scan, a reindex or a Git fetch, pull or push never blocks them. No article text is held in memory. Indexing parses batches in parallel while the previous batch is written, and commits in short transactions. Saves, creations, deletions, renames and watched changes reindex only the affected files, and links are re-resolved only where a target with the same filename appeared or disappeared. The window restores from the database at once: large file trees load after the first article, and later changes arrive as small catalog deltas triggered by native change events. In the reader, link resolution, titles and the Files tree come from one incremental index per workspace, so typing never revisits every path.

The debug executable is tested from an isolated folder with an empty PATH and no adjacent runtime. Git is optional and separately installed; Windows discovery checks its standard installation locations before PATH. Native folder dialogs and real remote authentication still require interactive acceptance. Weave Lite and dynamic preview builds remain read-only and do not call external services; the separate server build uses its same-origin HTTP API.

Limits: 4 MB per note, 1,000,000 notes and 32 GB of Markdown per workspace, 64 folder levels, and 100 nodes per displayed neighborhood. A first-opened workspace shows its tree after a walk and becomes fully searchable as background indexing completes (about a minute per 100,000 articles; searches meanwhile cover what is indexed). The database grows to roughly four times the Markdown it indexes. The reader keeps every article path of an open workspace in memory, which grows with workspace size. Symlinks/junctions are excluded. Multi-file transactions cannot eliminate the final filesystem race with unrelated applications. Android is not a supported platform.

Chunks retain stable IDs, content/source hashes, byte offsets and line ranges for future vector storage in the same database. No embedding or AI provider is implemented. A future generation adapter can consume the evidence bundle with its paths, lines and source hashes.
